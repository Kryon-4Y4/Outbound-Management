## 分支管理策略

本项目采用 **Git Flow** 分支模型，结合实际情况进行调整。

### 分支类型

```
┌─────────────────────────────────────────────────────────────────────┐
│                         分支模型图                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  main ─────●────────●────────●────────●────────●────────●────────► │
│           v1.0.0   v1.0.1   v1.1.0   v1.1.1   v1.2.0   v1.2.1      │
│            ▲                                              ▲         │
│            │                                              │         │
│  develop ──●────●────●────●────●────●────●────●────●──────●───────► │
│                 │         │    │              │                     │
│                 │    ┌────┘    └────┐   ┌─────┘                     │
│                 │    │              │   │                           │
│  feature/*      └───●┘              └──●┘                           │
│                 feature/login      feature/print                    │
│                                                                     │
│  hotfix/*                 ┌────●────┐                               │
│                          hotfix/bug-1                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 主要分支

| 分支 | 说明 | 保护级别 | 生命周期 |
|------|------|----------|----------|
| `main` | 生产环境分支，只接受合并请求 | 🔒 受保护 | 永久 |
| `develop` | 开发主分支，集成所有功能 | 🔒 受保护 | 永久 |

### 辅助分支

| 分支 | 命名规范 | 来源 | 合并目标 | 说明 |
|------|----------|------|----------|------|
| `feature/*` | `feature/<功能名>` | `develop` | `develop` | 新功能开发 |
| `hotfix/*` | `hotfix/<问题描述>` | `main` | `main` + `develop` | 生产环境紧急修复 |
| `release/*` | `release/<版本号>` | `develop` | `main` + `develop` | 版本发布准备 |

### 分支命名示例

```bash
# 功能分支
feature/user-auth          # 用户认证功能
feature/order-import       # 货单导入功能
feature/label-print        # 标签打印功能

# 修复分支
hotfix/fix-login-bug       # 修复登录问题
hotfix/encoding-issue      # 修复编码问题

# 发布分支
release/v1.2.0             # 1.2.0 版本发布
release/v1.3.0-beta        # 1.3.0 beta 版本
```

## 提交信息规范

本项目使用 [Conventional Commits](https://www.conventionalcommits.org/) 规范，配合 commitlint 进行校验。

### 提交格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 类型（Type）

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(order): 添加货单导入功能` |
| `fix` | 修复 Bug | `fix(auth): 修复登录状态失效问题` |
| `docs` | 文档变更 | `docs(api): 更新接口文档` |
| `style` | 代码格式调整（不影响功能） | `style: 统一缩进格式` |
| `refactor` | 代码重构 | `refactor(service): 优化打包服务逻辑` |
| `perf` | 性能优化 | `perf(query): 优化货单查询速度` |
| `test` | 测试相关 | `test: 添加用户模块单元测试` |
| `chore` | 构建/工具链变更 | `chore: 更新依赖版本` |
| `build` | 构建系统变更 | `build: 配置 Docker 构建` |
| `ci` | CI/CD 配置变更 | `ci: 添加自动化部署流程` |
| `revert` | 回滚提交 | `revert: 回滚错误的功能提交` |

### 范围（Scope）

范围表示修改影响的模块，可选但建议使用：

| 范围 | 说明 |
|------|------|
| `material` | 物料管理模块 |
| `product` | 产品管理模块 |
| `order` | 货单管理模块 |
| `packing` | 打包作业模块 |
| `print` | 标签打印模块 |
| `user` | 用户管理模块 |
| `auth` | 认证授权模块 |
| `api` | 接口层 |
| `ui` | 界面层 |
| `db` | 数据库 |
| `deploy` | 部署相关 |

### 提交示例

```bash
# 简单提交
feat(order): 添加货单批量删除功能

# 详细提交
feat(packing): 实现扫码打包功能

- 支持产品条码扫描识别
- 自动校验配柜数量
- 实时显示打包进度

Closes #123

# 修复提交
fix(print): 修复标签打印错位问题

修复 TSC 打印机在打印 80x60mm 标签时的偏移问题

# 重构提交
refactor(service): 重构打包记录查询逻辑

使用 MyBatis Plus 条件构造器替代原生 SQL，提高可维护性
```

### 提交注意事项

1. **原子性**：每次提交只包含一个功能点或修复点
2. **描述清晰**：`subject` 使用祈使句，描述做了什么而非状态
3. **关联 Issue**：修复 Bug 时在 footer 关联相关 Issue
4. **避免大提交**：大量修改应拆分为多个提交

## 代码审查流程

### 审查原则

```
┌─────────────────────────────────────────────────────────────┐
│                     代码审查流程图                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│  │ 功能开发  │───▶│ 本地测试  │───▶│ 提交 MR  │              │
│  └──────────┘    └──────────┘    └────┬─────┘              │
│                                       │                     │
│                                       ▼                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│  │ 合并代码  │◀───│ 审查通过  │◀───│ 代码审查  │              │
│  └──────────┘    └──────────┘    └────┬─────┘              │
│                                       │                     │
│                                       ▼                     │
│                                  ┌──────────┐              │
│                                  │ 需要修改  │──────────────┤
│                                  └──────────┘              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Merge Request 规范

#### MR 标题格式

```
[<type>][<scope>] <简要描述>

示例：
[feat][order] 添加货单导入导出功能
[fix][auth] 修复 JWT Token 过期问题
[refactor][db] 优化打包记录查询性能
```

#### MR 描述模板

```markdown
## 变更说明
简要描述本次变更的内容和目的。

## 变更类型
- [ ] 新功能 (feat)
- [ ] Bug 修复 (fix)
- [ ] 文档更新 (docs)
- [ ] 代码重构 (refactor)
- [ ] 性能优化 (perf)
- [ ] 测试添加 (test)
- [ ] 其他 (chore)

## 相关 Issue
关联的 Issue 编号：#123, #456

## 测试情况
- [ ] 本地测试通过
- [ ] 单元测试通过
- [ ] 集成测试通过

## 截图（如适用）
<!-- UI 变更请添加截图 -->

## 检查清单
- [ ] 代码符合项目规范
- [ ] 已添加必要的注释
- [ ] 已更新相关文档
- [ ] 没有引入新的警告
```

### 审查检查项

| 类别 | 检查项 |
|------|--------|
| **功能** | 代码是否实现了预期功能 |
| **逻辑** | 业务逻辑是否正确 |
| **规范** | 是否符合代码规范 |
| **安全** | 是否存在安全隐患 |
| **性能** | 是否有性能问题 |
| **测试** | 是否包含必要的测试 |
| **文档** | 是否需要更新文档 |

## 版本号管理

本项目采用 [语义化版本](https://semver.org/lang/zh-CN/)（Semantic Versioning）规范。

### 版本号格式

```
主版本号.次版本号.修订号

示例：1.2.3
```

| 版本号 | 递增条件 | 示例场景 |
|--------|----------|----------|
| 主版本号 | 不兼容的 API 修改 | 数据库结构调整、接口废弃 |
| 次版本号 | 向下兼容的功能新增 | 新增货单管理功能 |
| 修订号 | 向下兼容的问题修复 | Bug 修复、性能优化 |

### 版本标签

```bash
# 打标签
git tag -a v1.2.0 -m "版本 1.2.0 发布"

# 推送标签到远程
git push origin v1.2.0

# 推送所有标签
git push origin --tags
```

### 紧急修复流程

```bash
# 1. 从 main 创建 hotfix 分支
git checkout main
git pull origin main
git checkout -b hotfix/critical-bug

# 2. 修复问题并提交
git add .
git commit -m "fix: 修复严重 Bug"

# 3. 合并到 main 并发布
git checkout main
git merge hotfix/critical-bug
git tag -a v1.2.1 -m "紧急修复版本 1.2.1"
git push origin main --tags

# 4. 合并回 develop
git checkout develop
git merge hotfix/critical-bug
git push origin develop

# 5. 删除 hotfix 分支
git branch -d hotfix/critical-bug
git push origin --delete hotfix/critical-bug
```

## 冲突解决规范

### 预防冲突

1. **频繁拉取**：每天至少执行一次 `git pull`
2. **小步提交**：频繁提交小的变更，减少冲突范围
3. **及时沟通**：多人修改同一文件时提前沟通
4. **功能隔离**：不同功能使用不同分支开发

### 解决冲突步骤

```bash
# 1. 拉取最新代码
git pull origin develop

# 2. 如果出现冲突，查看冲突文件
git status

# 3. 编辑冲突文件，解决冲突
# 冲突标记格式：
# <<<<<<< HEAD
# 本地代码
# =======
# 远程代码
# >>>>>>> branch-name

# 4. 标记冲突已解决
git add <冲突文件>

# 5. 完成合并
git commit -m "merge: 解决与 develop 分支的冲突"
```

### 冲突解决原则

1. **理解双方变更**：不要盲目选择某一方
2. **保留必要代码**：确保功能完整性
3. **测试验证**：解决冲突后必须测试
4. **及时提交**：解决后立即提交，不要搁置

## 常用操作指南

### 日常开发流程

```bash
# 1. 开始新功能
git checkout develop
git pull origin develop
git checkout -b feature/new-feature

# 2. 开发过程中
git add .
git commit -m "feat(scope): 描述"

# 3. 推送分支
git push -u origin feature/new-feature

# 4. 创建 MR 请求合并到 develop

# 5. 合并后清理
git checkout develop
git pull origin develop
git branch -d feature/new-feature
```

### 常用命令速查

| 操作 | 命令 |
|------|------|
| 查看状态 | `git status` |
| 查看历史 | `git log --oneline --graph` |
| 查看差异 | `git diff` |
| 撤销修改 | `git checkout -- <file>` |
| 撤销暂存 | `git reset HEAD <file>` |
| 修改上次提交 | `git commit --amend` |
| 储藏变更 | `git stash push -m "描述"` |
| 恢复储藏 | `git stash pop` |
| 查看储藏列表 | `git stash list` |

### 储藏（Stash）使用场景

```bash
# 临时保存当前工作
git stash push -m "未完成的功能"

# 切换到其他分支处理紧急问题
git checkout hotfix/urgent

# 处理完后回到原分支
git checkout feature/xxx
git stash pop
```
